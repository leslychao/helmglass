# Helm Glass

Кабинет задач с изолированным браузером, подключениями сайтов и MCP для ChatGPT.
Функциональный контракт и источники оформления находятся в [docs](docs/README.md).
[Матрица приёмки](docs/acceptance.md) отделяет реализацию от фактически проверенных сценариев.

## Компоненты

- `backend/api` — Java 21 / Spring Boot 4.1, предметные операции REST и MCP,
  PostgreSQL, Liquibase, серверные события и постоянные файлы.
- `backend/browser-node` — назначения браузеров, зашифрованные профили подключений,
  одноразовые билеты просмотра и серверное ограничение управления.
- `backend/browser-session` — отдельный контейнер Chromium / Playwright / X display
  для каждой сессии. Просмотр и ввод используют раздельные серверные VNC-каналы.
- `backend/egress` — контролируемый выход каждой сессии в Интернет.
- `frontend` — Angular 22, кабинет пользователя и администратора.
- `deploy` — единый Compose, внутренний Nginx, Keycloak с темой Helm,
  OAuth2 Proxy, Redis, Vault и подготовка управляемых пользователей.

## Конфигурация и запуск

Нужны Docker CLI с Compose v2 и Linux shell. В Windows используйте Git Bash или WSL.
Сборка выполняется штатными Dockerfile; локальные Java и Maven для неё не нужны.

1. Скопируйте `deploy/.env.dev.example` в `deploy/.env.dev`, а
   `deploy/.env.local.example` в `deploy/.env.local`. Реальные файлы исключены из Git.
2. Заполните обязательные значения. `DEV_HOST` задаёт Docker-хост, `GLOBAL_NGINX_HOST`
   — независимо управляемый глобальный gateway. `PUBLIC_URL` и `PUBLIC_HOST` задают
   публичный адрес и имя. `NODE_ID` — постоянный UUID браузерного узла.
3. Используйте независимые случайные секреты для каждого стенда.
   `OAUTH2_COOKIE_SECRET` — 32 случайных байта в Base64.
   Пароли и остальные секреты должны быть криптографически случайными.
4. Один раз выполните `sh deploy/deploy-dev.sh deploy/.env.dev --vault-init`.
   Скрипт запускает только Vault, создаёт TLS CA, KV v2, Transit и AppRole, отзывает
   первоначальный root-токен и сохраняет `VAULT_UNSEAL_KEY`, `VAULT_ROLE_ID`,
   `VAULT_SECRET_ID` в выбранном исключённом из Git env-файле. Повторная инициализация
   не заменяет существующие ключи. Vault не имеет опубликованного порта.
   На dev ключ автоматической разблокировки хранится на том же стенде: это не даёт
   независимой защиты при компрометации хоста. Сохраняйте эти значения и volumes Vault.

На dev:

```sh
sh deploy/deploy-dev.sh deploy/.env.dev
```

Для Docker Compose `2.29.7-desktop.1`, где наблюдался `concurrent map writes`,
успешно проверен тот же запуск с `COMPOSE_PARALLEL_LIMIT=1` перед `sh`.
Это [штатный предел параллелизма Compose](https://docs.docker.com/compose/how-tos/environment-variables/envvars/#compose_parallel_limit),
а не изменение конфигурации приложения.

Скрипт выбирает env-файл явно, проверяет Compose, собирает образы, запрещает новые
назначения и ждёт подтверждённого освобождения браузеров. Неизвестное состояние узла
останавливает обновление. Деплой не закрывает рабочие браузеры принудительно;
серверный таймаут 15 минут применяется только к простою по функциональному контракту.
После обновления скрипт проверяет API и разрешает новые назначения.
При переходе со старой версии оставьте `PROFILE_ENCRYPTION_KEY` в env до первого
успешного деплоя. После освобождения браузеров скрипт переносит старые записи,
проверяет чтение каждой и только затем удаляет её старое значение. Повторный запуск
продолжает миграцию. После полного переноса скрипт удаляет старый ключ из env;
работающее приложение его не получает и прежнее хранилище не использует.
Если ожидание отменено оператором, запрет новых назначений сохраняется до завершённого
повторного запуска; уже открытые браузеры продолжают работать.
Предельное ожидание освобождения — 10 минут; его истечение прерывает обновление,
сохраняя браузеры и запрет новых назначений.

Конфигурация IDEA `Deploy dev` в `.run/` вызывает этот же скрипт через `$PROJECT_DIR$`.
Секреты и адреса в конфигурации IDEA отсутствуют.

Проверка обоих env-файлов без вывода секретов:

```sh
sh deploy/deploy-dev.sh deploy/.env.dev --config-only
sh deploy/deploy-dev.sh deploy/.env.local --config-only
```

Для самостоятельного local глобальный gateway не нужен. Создайте указанную в
`.env.local` внешнюю bridge-сеть с подсетью, содержащей `EDGE_NETWORK_ADDRESS`, затем
запустите основной Compose с явно выбранным `.env.local`. Публичный порт внутреннего
Nginx привязан к loopback. Рабочая приёмка проекта выполняется на dev.

## Публичный вход

Маршрут dev: клиент → глобальный Nginx → `helmglass-edge:8080` → компоненты.
Глобальный gateway развёртывается из самостоятельного проекта `nginx-edge-gateway`
его штатными скриптами. Он владеет сертификатом `helmg.ru` и централизованным продлением.
Для HTTPS включён HTTP/2: несколько вкладок и виджетов с SSE не исчерпывают
лимит HTTP/1.1-соединений браузера. Внутреннее проксирование и WSS сохраняют свой транспорт.
Сеть из `EDGE_NETWORK` должна существовать до запуска приложения.
Docker API `DEV_HOST:2375` предназначен только для доверенной сети управления.

Keycloak хранит пользователей в отдельной БД. OAuth2 Proxy хранит сессии кабинета
в Redis; браузер получает только защищённый cookie-билет. Управляемые `test` и `admin`
подготавливаются идемпотентно с паролями своего стенда и готовыми профилями.
OTP в realm Helm Glass отключён для кабинета и MCP; вход использует пароль.
Имя и фото меняются внутри профиля Helm. Фотографии хранятся в постоянном томе
артефактов, метаданные — в PostgreSQL; email доступен только для чтения.
`admin` получает роль приложения, без прав администратора Keycloak.
Bootstrap credentials Keycloak задаются отдельно. `KEYCLOAK_LIFECYCLE_SECRET` принадлежит
служебному клиенту удаления аккаунтов только realm Helm Glass. Подготовка не заменяет чужую запись
с совпавшим именем и не пересоздаёт существующий realm.

## ChatGPT

MCP Streamable HTTP: `https://helmg.ru/mcp`. Метаданные OAuth:
`https://helmg.ru/.well-known/oauth-protected-resource/mcp`.
OAuth-клиент `helmglass-chatgpt` использует PKCE S256 и callback
`https://chatgpt.com/connector_platform_oauth_redirect`. Если интерфейс подключения
запрашивает client ID, используйте `helmglass-chatgpt`; у публичного PKCE-клиента нет
client secret. Кабинет и ChatGPT имеют независимые сессии и отзыв доступа.
Для ChatGPT запрашивается `offline_access`: этот доступ сохраняется после выхода
из кабинета. MCP-вход требует собственного ввода учётных данных, а отключение
интеграции в кабинете отзывает её доступ независимо от сессии кабинета.

Включите поддерживаемый вашим аккаунтом режим подключения собственного MCP,
подключите этот адрес с OAuth и войдите в нужный аккаунт Helm Glass.
Helm предоставляет только пользовательские инструменты. По умолчанию GPT работает
автономно в рамках поручения. Ответы, выбор подключения и конкретные подтверждения
принимаются только от человека через native MCP elicitation в исходном GPT-чате;
секретный вход и ручное управление — в кабинете. Создание и редактирование черновиков
в кабинете сохраняются. Модель не может передать согласие через CONFIRM.
Проверку результата уже разрешённого действия при UNKNOWN GPT выполняет самостоятельно
через `tasks.respond.verification` после успешного наблюдения сайта; форма пользователя
для этого не нужна. UNKNOWN запрашивает продолжение агента и позволяет восстановить браузер.
Если исход не установлен, но продолжение безопасно без повтора прежнего действия, GPT
записывает UNCONFIRMED и продолжает; неопределённость сохраняется в истории.
Один исходный чат содержит одну незавершённую задачу. `tasks.create` создаёт и связывает
новую задачу, `tasks.bind` явно связывает задачу кабинета, `tasks.view` обновляет только
карточку. STOP окончателен; завершённую задачу можно явно продолжить, если чат свободен.

Виджет использует стандарт MCP Apps. Исходный чат определяется host-метаданными
`openai/session`, отдельно от экземпляра виджета. Если host их не передал или
отклонил автоматическое продолжение, интерфейс сообщает причину. Переданное host
сообщение не означает, что ChatGPT принял следующий шаг. После «Сохранить вход» GPT
сначала проверяет фактический доступ к нужному аккаунту. Само сохранение профиля
не доказывает успешный вход. /mcp использует Streamable HTTP; клиент должен поддерживать
elicitation form. Без него вопрос остаётся ожидающим с явной причиной.
Адрес UI-ресурса содержит SHA-256 опубликованного HTML и меняется вместе с его кодом.
После обновления сервера обновите личное подключение в ChatGPT, чтобы host перечитал
описания инструментов и новый адрес виджета, как предусмотрено
[порядком разработки плагина](https://developers.openai.com/plugins/build/app-quickstart).

Аудио распознаётся на сервере Helm; MCP передаёт текст и измерения. `audio.analyze`
запускает `transcript`/`full`, `audio.get` читает ограниченные страницы и состояние.
Оригинал сохраняется неизменным и доступен владельцу для скачивания в кабинете.
Контракт и ограничения — в [разделе «Аудио»](docs/Helm-Glass-functional-spec.md#10-аудио).

Модели — независимый Compose-проект на том же dev. Сначала задайте отдельный
случайный `AUDIO_TOKEN` (не менее 32 символов) в выбранном env-файле и разверните модели:

```sh
bash deploy/deploy-models.sh deploy/.env.dev
bash deploy/deploy-dev.sh deploy/.env.dev
```

`deploy/docker-compose.models.yml` создаёт закрытую сеть `helmglass-audio` без публичных
портов и использует существующий `helmglass_artifacts` только для чтения. Обычный
деплой приложения не пересоздаёт модели. Для проверки подстановок обоих стендов
оба скрипта поддерживают `--config-only` после пути env-файла. Сборка моделей требует
Интернета и места для FP32-экспорта; runtime работает в закрытой сети. Версии,
SHA-256 и точные зависимости находятся в `backend/audio-processor/model-lock.json`
и `requirements.lock`; расхождение контрольных сумм останавливает сборку/запуск.

## Данные и контракты

PostgreSQL — источник бизнес-состояния; миграции находятся в ресурсах API.
Артефакты записываются потоково в постоянный volume, готовность и целостность — в БД.
Credentials хранятся в Vault KV v2. Профили сайтов записываются потоково с gzip и
AES-256-GCM на постоянный volume браузерного узла; отдельный ключ каждой версии
обёрнут Vault Transit. Одна CAS-запись подключения содержит manifest профиля,
ревизии и независимо изменяемые credentials. Сначала устойчиво сохраняется файл,
затем подтверждается KV-запись. Незавершённая запись восстанавливается по журналу.
Лимит профиля — 256 МиБ сериализованных байтов до сжатия, записи — 16 МиБ,
порции — до 64 КиБ. До восстановления проверяется GCM-тег всего файла.
Недоступность Vault блокирует сохранение и восстановление, но не закрывает живой браузер.
Credentials доступны только приватному контроллеру выбранного подключения,
подставляются на точном origin без отправки формы. Сессии входа в Helm остаются в Redis.
Обычный повторный деплой сохраняет рабочие volumes и realm.
Резервные копии, восстановление из них, `prune` и очистка volumes в поставку не входят.

REST-схемы: [backend/api/openapi.yaml](backend/api/openapi.yaml).
MCP-схемы публикуются самим сервером через `tools/list` и `resources/list`.
После изменения MCP-контрактов выполните «Обновить инструменты» в настройках
подключённого Helm Glass Dev в ChatGPT; затем начните новый ответ. До обновления
ChatGPT может продолжать использовать прежние схемы и HTML виджета.
Изменяющие REST-команды требуют `Idempotency-Key`; браузерные операции — постоянный
`operationId`, обязательный `stepId`, ревизию поручения и поколение управления. После потери ответа
проверяйте сохранённый исход, а не отправляйте действие заново. `UNKNOWN` сохраняется
до достоверной проверки и блокирует дальнейшие изменения.

## Проверки приложения на dev

Обычные браузерные команды выполняет штатный Microsoft Playwright MCP без патчей;
версии закреплены в `backend/browser-session/package-lock.json`. Контракт команд и
фильтрация перед выдачей модели описаны в §9 [спецификации](docs/Helm-Glass-functional-spec.md).

После штатного деплоя интеграционные проверки обращаются к публичному адресу из
`HELM_TEST_ENV` (по умолчанию `deploy/.env.dev`) через обычный OIDC и PKCE:

```sh
python backend/api/tests/test_oauth_discovery.py
python backend/api/tests/test_dev_contract.py
python backend/api/tests/test_browser_execution.py
python backend/api/tests/test_connection_contract.py
python backend/api/tests/test_results.py
python backend/api/tests/test_business_steps.py
python backend/api/tests/test_mcp_audio.py
python backend/api/tests/test_viewer_revocation.py
node --test backend/browser-node/test/clipboard.test.mjs
python backend/api/tests/test_browser_clipboard.py
```

Аудиовыборка и эталоны закреплены в `backend/api/tests/audio-corpus.json`.
Подготовка открытых коротких записей и измерение на dev:

```sh
python backend/api/tests/prepare_audio_corpus.py
python backend/api/tests/evaluate_audio.py
```

Для отдельной проверки четырёх классов эмоций на закреплённых 20 записях:
`python backend/api/tests/prepare_audio_corpus.py --emotions`, затем
`python backend/api/tests/evaluate_audio.py --emotions`. Это малая диагностическая
выборка; отсутствие оценки и несовпадение с разметкой отражаются в результате.

`python backend/api/tests/verify_audio_recovery.py` — отдельная проверка сбоев на свободной
аудиоочереди dev: создаёт запись менее минуты, перезапускает только исполнитель моделей
и проверяет истёкший lease. Фактическая приёмка и ограничения находятся в
[разделе аудио](docs/acceptance.md#10-аудио).

Для проверки виджета в `test_results.py` нужны Node.js 24, зависимости
`backend/api/widget`, установленные через `npm ci`, и доступ к Docker API dev.
Гонки callback проверяются с управляемым host в Node.js на dev; это не проверка ChatGPT.
Проверка буфера использует опубликованный dev-код, установленный Chrome и зависимости
Playwright из `backend/browser-session`; создаёт и удаляет одно временное подключение.
Проверки создают данные приёмки;
административные сценарии используют отдельные временные учётные записи.
Эти проверки не заменяют работу в кабинете, настоящий ChatGPT и согласованный маршрут
входа на vk.com. Проверка пароля требует доступного аккаунту парольного сценария;
OTP/QR-вход не доказывает автоподстановку.
